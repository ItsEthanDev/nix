# Plan

Read the current target, project constraints, relevant interfaces, code, and existing tests. Investigate unknowns that could change the approach. If a finding changes intended behavior, obtain user direction before changing that target; a technical choice within accepted intent may be resolved in the plan. Identify the smallest sufficient implementation, any contract that consumers rely on, and direct evidence for the intended behavior. When module interfaces, seams, or testability materially affect the design, load `engineering-principles` and select **Design Deep Modules**. Agree on consumer-facing contracts before dependent implementation; consult `project-documentation` for their owner.

Order work into verifiable slices. Use the conventional `plan.md` and `tasks.md` when they add distinct value, and keep IDs on items the user may reference. Do not generate a full checklist for trivial work. Before implementation, check that intended behavior has planned evidence, that each task serves the current target, and that no plan or contract silently introduces new product obligations. Resolve conflicts in their owners or ask when intent is unclear.
